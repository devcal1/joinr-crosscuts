# M1.1 plan: maintenance upgrades

Status: **draft for Todd's approval** (M1.1 · 1.1). Researched 2026-10-10.

M1.1 is three small upgrades. Each one is its own release (decision on record), and none changes what users see. The step numbers are in `roadmap.md`.

## Summary

| Release | Version | What changes | Risk | Device update? |
|---|---|---|---|---|
| Stage 2: Node 22 | 0.1.1 | Base image `node:20-alpine` → `node:22-alpine` | Low | Yes |
| Stage 3: sharp 0.35 | 0.1.2 | `sharp` ^0.33.5 → ^0.35.5 | Low (tested, see below) | Yes |
| Stage 4: Actions | 0.1.3 | CI actions moved to Node-24 majors | Low, CI only | No (see "How a CI-only change releases") |

The order stays as the roadmap has it. Node 22 goes first because the app currently runs on Node 20, which reached end of life in April 2026 and gets no more security fixes. The Actions upgrade goes last because it is hygiene, not a fix: CI already works (reasons below).

## Stage 2: Node 20 → 22

**Change:** one line in `crosscuts/app/Dockerfile`: `FROM node:22-alpine`. Nothing else in the app changes. The lockfile is untouched.

**Why it is safe:**
- `better-sqlite3` 11.10.0 (the locked version) ships prebuilt binaries for Node 22 (`node-v127`) on Alpine for both x64 and arm64. Checked against its release assets. The image has no compiler, so a missing binary would fail the CI build rather than ship broken.
- `sharp` 0.33.5, `express` 4, `multer` 1.4.5-lts and `@google/generative-ai` 0.21 all accept Node 22.
- I'm keeping the floating `22-alpine` tag rather than pinning a patch level, so each release picks up Node and Alpine security patches. The compose file still pins the finished image by digest, so the device only gets what CI tested.

**Why 22 and not 24:** Node 24 would need `better-sqlite3` 12 or later (11.10 has no Node 24 binaries). That's a bigger change on the module that holds the live schedule. Node 22 is supported until April 2027. Moving to Node 24 should be a later release of its own, together with better-sqlite3, before April 2027.

**Checks:**
- Add one smoke check to `ci/smoke.sh`: `node -v` inside the image starts with `v22.`, so the base image change is proven, not assumed.
- Local run: only a quick sanity check. The dev box runs Node 24 through the shim, so it says nothing about Node 22. CI is the real proof.
- CI green on both architectures, including the existing upload and thumbnail smoke test.
- On the device (2.3): log in, the board loads, photo search shows thumbnails, over both LAN and Tailscale. **The carried M1 LAN check is done in the same visit.**

## Stage 3: sharp 0.33 → 0.35

**Change:** `npm install sharp@^0.35.5` in `crosscuts/app` (updates `package.json` and the lockfile, including the `@img/sharp-*` platform packages). Expect no code change beyond correcting one comment in `routes/photos.js` that names "sharp 0.33".

**Breaking changes in 0.34 and 0.35, and whether they affect us:**

| Change | Affects us? |
|---|---|
| Node 18 dropped, minimum 20.9 (0.35) | No: Node 22 by then |
| `install` script removed. Prebuilt binaries or nothing (0.35) | No: linuxmusl x64 and arm64 binaries are published for 0.35.5, and the lockfile already carries the musl packages |
| `failOnError`, `paletteBitDepth`, old `sharpen` options removed (0.35) | No: unused |
| New `limitInputChannels`, default 5 (0.35) | No: photos have 4 channels at most |
| `removeAlpha`, GIF loop default, multi-input arrays (0.34) | No: unused |
| `.rotate()` with no angle | Unchanged: the docs say it still calls the new `.autoOrient()` "for backwards compatibility" |

**Tested now:** I ran our exact upload pipeline (`metadata()`, `.rotate()`, `.resize({ width, withoutEnlargement })`, `.webp({ quality: 80 })`) under 0.33.5 and 0.35.5. The input was a JPEG tagged EXIF orientation 6 (stored landscape, displayed portrait), plus the 1×1 PNG from the smoke test. Both versions gave identical results: stored size 20×40, thumbnail 10×20 WebP, PNG 1×1.

**Checks:**
- Add a smoke test: upload a small JPEG tagged orientation 6 and assert the stored width and height are swapped. Today's smoke test uses a 1×1 PNG, which can't detect a rotation regression. This test is the main protection for this release.
- CI green on both architectures.
- On the device (3.3): upload a portrait phone photo, and check its thumbnail is upright and the full image opens.

## Stage 4: GitHub Actions to Node-24 majors

**Change** (`.github/workflows/publish.yml` only):

| Action | Now | To |
|---|---|---|
| `actions/checkout` | v4 | v7 |
| `actions/upload-artifact` | v4 | v7 |
| `actions/download-artifact` | v4 | v8 |
| `docker/setup-buildx-action` | v3 (node20) | v4 |
| `docker/build-push-action` | v6 (node20) | v7 |
| `docker/login-action` | v3 (node20) | v4 |

The targets are the newest major of each; all declare `node24`, checked in each action's `action.yml`. In 4.1 I'll read each major's release notes for breaking inputs before changing anything. The inputs we use most (`sparse-checkout`, `merge-multiple`, `pattern`, `cache-to ... ignore-error`, `provenance`) are the likely trouble spots.

**Why it isn't urgent:** GitHub switched runners to Node 24 on 16 June 2026 and removed Node 20 on 23 September 2026. Our 0.1.0 run went green on 10 October, after the removal, so the old actions are being run on Node 24 and work. Upgrading removes the risk that one of them breaks under a runtime it was never written for.

### How a CI-only change releases

The version guard only demands a bump when `crosscuts/app/` changes, so a workflow-only push gets past it. But a push to `main` always runs the merge job, which refuses to overwrite the existing version tag. Without a bump, the run would build and smoke-test fine and then go red at the merge job.

**Recommended:** bump the version anyway (0.1.3) in the same commit. CI publishes a 0.1.3 image built by the new actions, which proves the whole publish path end to end, including the merge job and the digest line. **Don't pin it in the Tenon store** and don't ask Todd to update: the app code is the same as 0.1.2. 0.1.3 simply sits in the registry, and the next real release supersedes it.

**Rejected:** teaching the merge job to skip publishing when nothing under `crosscuts/app/` changed. It adds logic to the release guard, and it would leave the new merge-job actions untested until the next app release.

## Per-release routine (2.2, 3.2, 4.2)

1. Bump `version` in `crosscuts/app/package.json` and the top-level version in `crosscuts/app/package-lock.json`, then commit.
2. **Todd OK**, then push `joinr-crosscuts` `main`, and CI runs green on both architectures.
3. Take the `image:` line from the run summary, or read the digest anonymously from `ghcr.io/v2/devcal1/crosscuts-web/manifests/<version>`.
4. In tenon-umbrel-store: pin the image line, and bump `version:` and `releaseNotes:` in `tenon-joinr-crosscuts/umbrel-app.yml`. **Todd OK**, then push. (Skipped for 0.1.3.)
5. Todd clicks Update, and the device checks for that stage follow.
6. If a release misbehaves on the device: re-pin the previous version's image line in the store with a higher store `version:`. Nothing in M1.1 touches the database, so rolling back is safe.

## Out of scope (noted, not done)

- Node 24 together with better-sqlite3 12 or later (before Node 22's end of life in April 2027).
- `multer` 1.x has published advisories; 2.x is the maintained line. Uploads need a login, so the exposure is limited. It's a candidate for its own small release, not part of M1.1.
- `@google/generative-ai` is deprecated in favour of `@google/genai`. It still works; revisit when tag suggestion is next touched.
