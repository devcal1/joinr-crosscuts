# M1.1 plan: maintenance upgrades

Status: **approved by Todd 2026-10-10** (M1.1 · 1.1). Researched 2026-10-10. Todd chose **Node 24** (not 22) on 2026-10-10.

M1.1 is four small upgrades. Each one is its own release (decision on record), and none changes what users see. The step numbers are in `roadmap.md`.

## Summary

| Release | Version | What changes | Risk | Device update? |
|---|---|---|---|---|
| Stage 2: database library | 0.1.1 | `better-sqlite3` 11.10.0 → 12.9.0, still on Node 20 | Low | Yes |
| Stage 3: Node 24 | 0.1.2 | Base image `node:20-alpine` → `node:24-alpine` | Low | Yes |
| Stage 4: sharp 0.35 | 0.1.3 | `sharp` ^0.33.5 → ^0.35.5 | Low (tested, see below) | Yes |
| Stage 5: Actions | 0.1.4 | CI actions moved to Node-24 majors | Low, CI only | No (see "How a CI-only change releases") |

**Why this order:**
- Node 24 needs `better-sqlite3` 12 or later, and changing both together would put two changes in one release. So the database library goes first, on its own, while Node stays at 20.
- Node 24 follows straight after, to get off Node 20. Node 20 reached end of life in April 2026 and gets no more security fixes.
- The Actions upgrade goes last because it is hygiene, not a fix: CI already works (reasons below).

**Why 24:** it is supported until 30 April 2028, a year longer than Node 22, and it matches the dev PC (which runs Node 24). Node 26 becomes long-term support on 28 October 2026 and is the target for the next Node change.

## Stage 2: better-sqlite3 11.10.0 → 12.9.0

**Change:** `npm install better-sqlite3@12.9.0` in `crosscuts/app` (`package.json` and the lockfile). Node stays at 20. No code change.

**Why 12.9.0 exactly (pinned, not `^12`):**
- 12.9.0 is the **last version with prebuilt binaries for both Node 20 and Node 24** on Alpine, x64 and arm64. Checked against its release assets.
- 12.10.0 removed the Node 20 binaries. The image has no compiler, so a later 12.x would fail to build on Node 20.
- The 12.x and 13.x lines include several releases marked "not viable" by their own authors, so using a known-good version matters.
- Pinning means Stage 3 needs no package change at all.

**What changed between 11.10 and 12.9:**
- The only breaking change is in 12.0.0: Node 18 and some old Electron versions were dropped.
- Everything else is new SQLite versions (3.49 → 3.53.0) and build fixes. The JavaScript API we use is unchanged.
- The database file format stays compatible both ways, so an older build can still open a file written by this one.

**Checks:**
- Smoke step 0: the better-sqlite3 version in the image must match the lockfile, and the SQLite version is printed (12.9.0 bundles SQLite 3.53.0).
- CI green on both architectures. The existing smoke suite exercises the database heavily: the migration runner and its `VACUUM INTO` backup, the board and schedule APIs, login and sessions, the audit log, and the old-image upgrade rehearsal.
- Local run: not meaningful here, because the dev box uses `node:sqlite` through the shim, not better-sqlite3. CI is the real proof.
- On the device (2.3): log in, the board loads with its weeks, and one board edit saves and shows in the audit log; over LAN and Tailscale. **The carried M1 LAN check is done in the same visit.**

## Stage 3: Node 20 → 24

**Change:** one line in `crosscuts/app/Dockerfile`: `FROM node:24-alpine`. No other change in the app, and the lockfile is untouched.

**Why it is safe:**
- `better-sqlite3` 12.9.0 (from Stage 2) has Node 24 (`node-v137`) binaries for Alpine x64 and arm64.
- `sharp` (0.33.5 and 0.35.5), `express` 4, `multer` 1.4.5-lts and `@google/generative-ai` 0.21 all accept Node 24.
- I'm keeping the floating `24-alpine` tag rather than pinning a patch level, so each release picks up Node and Alpine security patches. The compose file still pins the finished image by digest, so the device only gets what CI tested.

**Checks:**
- Smoke step 0 (added in 2.1) checks the Node major in the image against the Dockerfile `FROM` line, so it proves Node 24 with no script change.
- Watch: `node:24-alpine` ships npm 11, whose newer releases print "install-scripts" warnings. better-sqlite3 needs its install script to fetch its binary. Locally (npm 11.19) the script still ran and the binary loaded, and CI will confirm it in the image.
- Local run: a useful sanity check this time, since the dev box also runs Node 24 (through the shim).
- CI green on both architectures.
- On the device (3.3): log in, the board loads, photo search shows thumbnails; over LAN and Tailscale.

## Stage 4: sharp 0.33 → 0.35

**Change:** `npm install sharp@^0.35.5` in `crosscuts/app` (updates `package.json` and the lockfile, including the `@img/sharp-*` platform packages). Expect no code change beyond correcting one comment in `routes/photos.js` that names "sharp 0.33".

**Breaking changes in 0.34 and 0.35, and whether they affect us:**

| Change | Affects us? |
|---|---|
| Node 18 dropped, minimum 20.9 (0.35) | No: Node 24 by then |
| `install` script removed. Prebuilt binaries or nothing (0.35) | No: linuxmusl x64 and arm64 binaries are published for 0.35.5, and the lockfile already carries the musl packages |
| `failOnError`, `paletteBitDepth`, old `sharpen` options removed (0.35) | No: unused |
| New `limitInputChannels`, default 5 (0.35) | No: photos have 4 channels at most |
| `removeAlpha`, GIF loop default, multi-input arrays (0.34) | No: unused |
| `.rotate()` with no angle | Unchanged: the docs say it still calls the new `.autoOrient()` "for backwards compatibility" |

**Tested now:** I ran our exact upload pipeline (`metadata()`, `.rotate()`, `.resize({ width, withoutEnlargement })`, `.webp({ quality: 80 })`) under 0.33.5 and 0.35.5. The input was a JPEG tagged EXIF orientation 6 (stored landscape, displayed portrait), plus the 1×1 PNG from the smoke test. Both versions gave identical results: stored size 20×40, thumbnail 10×20 WebP, PNG 1×1.

**Checks:**
- Add a smoke test: upload a small JPEG tagged orientation 6 and assert the stored width and height are swapped. Today's smoke test uses a 1×1 PNG, which can't detect a rotation regression. This test is the main protection for this release.
- CI green on both architectures.
- On the device (4.3): upload a portrait phone photo, and check its thumbnail is upright and the full image opens.

## Stage 5: GitHub Actions to Node-24 majors

**Change** (`.github/workflows/publish.yml` only):

| Action | Now | To |
|---|---|---|
| `actions/checkout` | v4 | v7 |
| `actions/upload-artifact` | v4 | v7 |
| `actions/download-artifact` | v4 | v8 |
| `docker/setup-buildx-action` | v3 (node20) | v4 |
| `docker/build-push-action` | v6 (node20) | v7 |
| `docker/login-action` | v3 (node20) | v4 |

The targets are the newest major of each; all declare `node24`, checked in each action's `action.yml`. In 5.1 I'll read each major's release notes for breaking inputs before changing anything. The inputs we use most (`sparse-checkout`, `merge-multiple`, `pattern`, `cache-to ... ignore-error`, `provenance`) are the likely trouble spots.

**Why it isn't urgent:** GitHub switched runners to Node 24 on 16 June 2026 and removed Node 20 on 23 September 2026. Our 0.1.0 run went green on 10 October, after the removal, so the old actions are being run on Node 24 and work. Upgrading removes the risk that one of them breaks under a runtime it was never written for.

### How a CI-only change releases

The version guard only demands a bump when `crosscuts/app/` changes, so a workflow-only push gets past it. But a push to `main` always runs the merge job, which refuses to overwrite the existing version tag. Without a bump, the run would build and smoke-test fine and then go red at the merge job.

**Recommended:** bump the version anyway (0.1.4) in the same commit. CI publishes a 0.1.4 image built by the new actions, which proves the whole publish path end to end, including the merge job and the digest line. **Don't pin it in the Tenon store** and don't ask Todd to update: the app code is the same as 0.1.3. 0.1.4 simply sits in the registry, and the next real release supersedes it.

**Rejected:** teaching the merge job to skip publishing when nothing under `crosscuts/app/` changed. It adds logic to the release guard, and it would leave the new merge-job actions untested until the next app release.

## Per-release routine (2.2, 3.2, 4.2, 5.2)

1. Bump `version` in `crosscuts/app/package.json` and the top-level version in `crosscuts/app/package-lock.json`, then commit.
2. **Todd OK**, then push `joinr-crosscuts` `main`, and CI runs green on both architectures.
3. Take the `image:` line from the run summary, or read the digest anonymously from `ghcr.io/v2/devcal1/crosscuts-web/manifests/<version>`.
4. In tenon-umbrel-store: pin the image line, and bump `version:` and `releaseNotes:` in `tenon-joinr-crosscuts/umbrel-app.yml`. **Todd OK**, then push. (Skipped for 0.1.4.)
5. Todd clicks Update, and the device checks for that stage follow.
6. If a release misbehaves on the device: re-pin the previous version's image line in the store with a higher store `version:`. No M1.1 release adds a migration, and the SQLite file format is compatible both ways, so rolling back is safe, including after Stage 2.

## Out of scope (noted, not done)

- Node 26 (long-term support from 28 October 2026, supported to April 2029): the next Node change, well before Node 24's end of life in April 2028.
- `better-sqlite3` 13 (a rewrite onto N-API; needs Node 22 or later) and later 12.x patch releases with newer SQLite fixes: a separate release after Stage 3, if wanted.
- `multer` 1.x has published advisories; 2.x is the maintained line. Uploads need a login, so the exposure is limited. It's a candidate for its own small release, not part of M1.1.
- `@google/generative-ai` is deprecated in favour of `@google/genai`. It still works; revisit when tag suggestion is next touched.
