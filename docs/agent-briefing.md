## 1. What this is and who uses it

**TH Cabinets** is a small joinery/cabinet-making business. The app is a
self-hosted web app running on the owner's **Umbrel** home server (a
Docker-based self-hosting OS) on the workshop LAN. It's distributed through a
personal Umbrel "community app store", and this repo is that store.

It started as a photo library and has grown into the business's **day-to-day
operations tool**. The most important part now is the **schedule board**. It
replaced a physical whiteboard-and-magnets fortnightly schedule and runs
full-time on a **workshop TV**, driven by a laptop at 1920×1080.

| Audience | Uses |
|---|---|
| Workshop staff (on the TV / LAN) | Schedule board: who's on which job, which day, manufacturing vs installing |
| Owner (Todd) | Everything. Doesn't watch the TV, so wants to be *told* about events that matter (see §7) |
| Customers in the showroom | Read-only photo search of past jobs |

Workers are managed in-app. On first install the app seeds a starter list of
six (Blay, Sam, Darcy, Shooter, Moo, Michael). The real team is bigger: the
Workshop Scheduler notes (§8) list about 13 people across CNC, manufacturing,
paint, install and deliveries. The live roster on the device hasn't been
checked for this doc.

## 2. Current capabilities (v1.9.0)

### Schedule board: `/schedule.html` (the core product)
- Shows **one week at a time** (Mon–Fri columns). It has two panels,
  **Manufacturing** and **Installing**, with jobs as rows. You can browse weeks
  with arrows or a date picker, which snaps to the Monday.
- **Jobs** are created by typing a name, and autocomplete reuses existing
  jobs. One job can have rows in both panels and across many weeks, sharing
  one name and one set of notes.
- **Worker chips** are assigned per day per row, colour-coded per worker. They
  stack in a two-row, column-major grid.
- **Day flags**: a per-day "locked in with client" marker.
- **Notes** per job. The notes icon turns orange when a job has notes.
- **Panel alignment**: a job in both panels sits on the same line, matched by
  normalised name.
- **Drag to reorder** rows within a panel. **Move a row a week** back or
  forward, **duplicate to next week**, or **remove** a row.
- **"To start" backlog** (left sidebar, new in 1.9.0): jobs not yet
  scheduled. You can add them by hand, drag them into either panel, or drag a
  scheduled row back onto it.
- **"Finish week"** (new in 1.9.0): a dialog asks, for each job in the week,
  whether it is *not started*, *still manufacturing*, *ready to install* or
  *complete*. It then sets up next week: rows are carried forward with the same
  worker assignments, and not-started jobs go to the backlog. **"Complete"
  currently records nothing**, so completed jobs simply drop off.
- **Exports**: print/PDF and a **JPG export that is hand-drawn to canvas**
  (not a screenshot).
- **No login.** Anyone on the LAN can view and edit it, the same trust model
  as the whiteboard. This is a deliberate auth carve-out at the Umbrel proxy.

### Photo library
- **`/search.html`** is customer/showroom-facing. It does live fuzzy search
  over photo tags (fuse.js) and is read-only, with no chrome.
- **`/admin.html`** is staff-facing. It has three parts:
  - upload with shared tags and optional **Gemini AI tag suggestions** (opt-in, needs a free key file)
  - **bulk import** from a folder-per-category layout
  - a manage table for inline tag edits, appends and per-photo AI suggest
- Uploads get thumbnails generated by `sharp`.

### Other
- **`/workers.html`** manages the roster: add, rename, pick a hue, archive.
  There's no hard delete, so past weeks stay accurate.
- **`/` (index)** is a landing page linking to everything.
- Every page except the schedule sits behind the **Umbrel login**. There is no
  app-level auth or user accounts.

## 3. Architecture

- **Backend**: a single Node/Express process with all routes in one file,
  `thcabinets-splash/app/server.js` (~970 lines). It uses `better-sqlite3` in
  WAL mode, `multer` for uploads, `sharp` for thumbnails and
  `@google/generative-ai` for tag suggestions.
- **Frontend**: plain HTML/CSS/JS, **no framework, no build step, no
  bundler**. This is a deliberate choice. There are five pages, and
  `schedule.js` is the biggest file at ~1,320 lines. Shared helpers are in
  `shared.js` (`api()`, `toast()`, `guarded()`, `hueColors()`). Icons
  (Phosphor, regular weight only) and fuse.js are vendored for offline LAN use.
- **CSS is page-local on purpose.** The schedule runs at about 1.2× scale for
  TV legibility, and admin is deliberately darker. Only genuinely shared
  tokens live in `tokens.css`.
- **Deployment**:
  1. Push to `master`.
  2. GitHub Actions builds the image and runs a **real smoke test against a
     live container** (photos, schedule, backlog and finish-week APIs).
  3. CI then publishes multi-arch (amd64 + arm64) to
     `ghcr.io/devcal1/thcabinets-web:latest`.
  4. The owner hits **Update** on the Umbrel dashboard. Umbrel only offers the
     update if `version:` in `umbrel-app.yml` was bumped.
- **Persistence**: Umbrel volumes under `data/` hold uploads, the DB and
  config (the Gemini key). The code lives only in the image.

### Data model (`app/db.js`, all in one SQLite file, `photos.db`)

| Table | Holds |
|---|---|
| `photos` | filename, thumb, dimensions, `tags` (a comma string) |
| `workers` | name, hue, archived, sort_order |
| `jobs` | **name, notes, archived only.** No client, address, value, dates or status |
| `week_rows` | job × week_start × panel (`manufacturing`/`installing`) × sort_order |
| `assignments` | week_row × day (mon–fri) × worker |
| `day_flags` | week_row × day ("locked in") |
| `backlog` | job (unique) × sort_order (1.9.0) |

Photos and jobs are **not linked**. A job has no lifecycle state: where it's
"up to" is implied only by which week/panel rows exist.

### API surface
- **Photos**: `GET/POST /api/photos`, `PATCH/DELETE /api/photos/:id`, `POST /api/suggest-tags`
- **Schedule**:
  - `GET /api/schedule?week=` returns weeks, rows, assignments, flags and the backlog
  - `GET/POST /api/workers`, `PATCH /api/workers/:id`
  - `GET /api/jobs`, `PATCH /api/jobs/:id`
  - `POST /api/rows`, `DELETE /api/rows/:id`, `POST /api/rows/:id/duplicate`
  - `PATCH /api/rows/:id/move`, which multiplexes four modes: `direction`, `toIndex`, `week`, `backlog`
  - assignments and flags endpoints
  - `POST /api/jobs/backlog`, `DELETE /api/jobs/backlog/:id`, `POST /api/jobs/backlog/:id/place`
  - `POST /api/rows/finish-week`
- **Health**: `GET /healthz`

## 4. Hard constraints (non-negotiables)

Any direction you propose has to live within these, or argue explicitly for
changing one.

1. **Bump `version:` in `umbrel-app.yml` on every app-code change**, or the
   change never reaches the device.
2. **Code ships as a published image.** `data/` is storage only.
3. **Never rename `photos.db`.** It holds the entire live schedule, and a
   rename silently boots an empty board.
4. **The schedule holds real production data.** Anything touching stored data
   (schema, migrations, bulk deletes) needs explicit data-loss reasoning and
   owner sign-off.
5. **Never uninstall/reinstall** the app without explicit confirmation, because
   it wipes everything.
6. **No build step, framework or bundler.**
7. **Page-local CSS is deliberate**, so don't "fix" the duplication.
8. **The JPG export is hand-drawn.** Any new visual on the board must be
   mirrored in `exportJpg()` in `schedule.js`, or it silently disappears from
   exports. This has bitten before.
9. **Auth whitelist trap.** The board is ungated through
   `PROXY_AUTH_WHITELIST` in `docker-compose.yml`, which matches *paths*. A new
   API path the board uses silently redirects the TV to a login (302) unless it
   is whitelisted. That's why new board behaviour prefers extending existing
   routes, e.g. `PATCH /api/rows/:id/move`. Conversely, owner-only features
   should sit on paths *outside* the whitelist.

Working style: the owner leans on CI smoke tests rather than local mock rigs.
Development happens on a Windows box where `better-sqlite3` won't build and
Docker isn't installed. Never push without being told to.

## 6. Known issues and deferred items

- **Uncommitted WIP** in the working tree: a `GET /api/tags` endpoint plus an
  admin filter bar (5 files, unreviewed). It ships as its own reviewed release
  or not at all. It has known bugs: stale tag counts, and a stale cache after
  inline edits.
- **Touch input**: row drag uses HTML5 drag-and-drop, which needs a mouse. A
  touchscreen in the workshop would need a rewrite to pointer events.
- **No `package-lock.json`**: each build resolves dependencies fresh, so the
  amd64 and arm64 images can differ.
- **Fonts**: `tokens.css` loads Inter from Google Fonts, which blocks rendering
  on a LAN with no internet. Inter should be vendored.
- **Timezone**: `/api/schedule` with no `?week=` defaults "today" in UTC, so it
  is wrong on Monday mornings AEST. The business is in **Australia/Sydney**.
- **Orphan rows**: historical orphan `day_flags` rows sit in production. A
  cleanup sweep needs owner sign-off.
- **Monolithic `server.js`**: splitting it into route modules is scoped but
  not done.
- **Auth**: there's no app-level auth or user accounts. A bcrypt +
  `express-session` design was scoped but not built.
- **Bulk-import wording**: the root-folder grouping doesn't match the UI copy.
  The intended behaviour still needs deciding.
- **CI stalls**: the multi-arch QEMU build has stalled before. The durable fix
  is native arm64 runners.

## 7. In-flight design: invoicing alerts (not approved, not built)

This is the next feature on the table and the clearest signal of where the
owner wants to go. **Problem**: the owner doesn't watch the TV, so the app
needs to say when to invoice:

- a **deposit** invoice when a job is first scheduled
- a **final** invoice when a job is marked **Complete** in Finish week

Today "Complete" stores nothing.

Owner's answers so far:
- **Alerts**: an instant push, plus a weekly round-up (Friday 12pm Sydney)
  that repeats until cleared.
- **Channels**: ntfy phone push plus email forwarding.
- **Page**: an owner-only `/invoicing.html` that staff and the TV never see.
- **Accounting**: no integration. "Invoiced" is marked by hand with a typed
  reference.
- **Remote access**: Tailscale is available, so links can reach the page.

A draft spec exists:
- new tables `billing_events` and `app_meta`
- a one-time backfill
- gated `/api/billing/*` routes
- an `app/notify.js` sweeper

**The owner has withheld approval for the new tables and backfill and says the
design "still needs work."** Treat it as open for discussion, not settled.

## 8. Related concept work: the "Workshop Scheduler" (read this first)

The owner has a separate, more ambitious design for scheduling, written up
in Google Drive under `projects/Workshop Scheduler/`, files 01–07, dated
9–10 Sep 2026. No code exists for it yet. **It bears directly on this app's
future, so read those files before proposing schedule features here.**

In short:

- **What it is.** An optimising scheduler. **Google OR-Tools** (CP-SAT,
  running as a Python solver microservice) does the sequencing. An **LLM
  layer** turns messy input ("CNC's down till Thursday") into constraints and
  explains the results. The LLM must never do the scheduling maths itself.
- **The workshop model** (files 02–06):
  - **Stages**: cut & edge → kit → assemble → inspect → paint (two-pac only,
    in-house) → transport & install → a return visit to hang doors (painted
    jobs with stone benchtops only).
  - **Branching**: the benchtop type decides whether install is one visit or
    two.
  - **External stone wait**: the return visit is pencilled in 7–10 working
    days after the carcass install, then locked when the stone supplier
    confirms.
  - **Staff**: about 13 people, with per-person skills and stages they can do
    and one speed factor each. Paint is the scarcest skill (Sam, with Aaron as
    backup).
  - **Machines**: one CNC and one edgebander, which is a choke point.
  - **Assembly floor**: one shared space budget, where a job's footprint
    depends on its state.
  - **Transport**: 2 trucks (a cap of 2 full-kitchen installs a day) plus a van
    and utes for small jobs.
  - **Hours**: 38 per person per week.
  - **Job size and durations**: size is measured in sheets, and durations
    scale with sheet count.
  - **Objective**: throughput, then deadlines, then even utilisation. It also
    allows manual pinning, and re-solves automatically with a bias against
    moving jobs that are already scheduled.
- **The big decision** (file 07): the scheduler becomes a module of
  **Joinr**, the owner's quoting product. Joinr runs as a cloud SaaS (Next.js
  on Vercel, Supabase, plus the solver service). A won quote flows straight
  into a scheduled job. File 07 records as **decided** that *TH Cabinets will
  run its own workshop as tenant #1 on that cloud SaaS ("dogfooding"), rather
  than as a separate in-house Umbrel deployment.* Files 01, 02 and 06 still
  list "relationship to the existing Umbrel system" as an open question.
- **Data-model rule from file 07**: a job must stand on its own. It can come
  from a won quote *or* be entered directly, so the scheduler must never
  assume a quote exists.

**What this means for the discussion.** The most important open question is
what role this Umbrel app plays once the Workshop Scheduler exists. Some
possible roles:

- **A bridge.** It keeps running the live board until the SaaS version can
  take over, so it should get only low-risk improvements and nothing that
  deepens the gap with Joinr's data model.
- **A prototype or proving ground.** Things like Finish week, the backlog and
  invoicing alerts get tested here on the real floor before being rebuilt in
  Joinr.
- **A permanent in-house display.** It stays as the LAN/TV board and reads
  from the SaaS.
- **Retirement.** It is wound down once the workshop moves over, which then
  needs a plan for migrating `photos.db` (schedule history and the photo
  library).

The answer changes how much to invest in the questions below. In particular,
a schema for the job lifecycle (Q1) should probably **mirror Joinr's job
structure and the scheduler's stages** rather than being designed
independently.

## 9. Strategic questions worth discussing

These are prompts, not decisions. They're the tensions the current build
surfaces:

0. **This app vs. the Workshop Scheduler / Joinr** (see §8). Settle this
   first, because everything else depends on it.
1. **Jobs as first-class entities.** `jobs` is just a name and notes. Invoicing,
   reporting and history all want a job *lifecycle* (quoted → scheduled →
   manufacturing → installing → complete → invoiced), plus client and
   address, value and dates. Should that be added deliberately in one go,
   rather than piecemeal per feature? Every option is a schema change on live
   data (constraint 4).
2. **Photos ↔ jobs.** The photo library and the schedule share a DB but know
   nothing about each other. Should finished jobs feed the showroom gallery
   (e.g. "upload photos for this completed job")?
3. **Board vs. back office.** The board is ungated and whiteboard-simple by
   design. Owner-only features (invoicing, money, client data) need a gated
   surface. Is it time for a real owner area, and for app-level auth (the
   scoped bcrypt + session design)?
4. **Notifications/outbound.** ntfy and email would be the app's first
   outbound network dependency. How should failures, retries and an offline
   LAN be handled?
5. **Scale of the codebase.** `server.js` and `schedule.js` are each over
   1,000 lines with no framework or build step. Is modularising (still
   build-free) a prerequisite for the next wave of features?
6. **Planning horizon.** The board shows one week, and the backlog isn't
   ordered by date. The demand for capacity and lookahead planning is already
   established: it's the whole point of the Workshop Scheduler (§8). The open
   question is whether *any* of that belongs in this app, for example simple
   lookahead or capacity hints, or whether it waits for the solver.
7. **Hardware assumptions.** Today it's a laptop-driven TV with a mouse. A
   touch panel, phone use by installers on site, or offline tolerance would
   each change the UI approach.
8. **Reliability hygiene** before growth: lockfile, vendored fonts, timezone
   fix, native arm64 CI, backup/restore of `photos.db` (there's currently no
   documented backup story).

## 10. Ground rules for the discussion

- The owner is practical and protective of the live schedule. Favour small,
  shippable, reversible steps, and flag data risk up front.
- When proposing a feature, say which **constraints in §4** it touches. Pay
  particular attention to schema changes, the auth whitelist, and the
  `exportJpg` mirror.
- For *this* app, don't assume accounting integrations, cloud services or
  frameworks are welcome. Ask first. The cloud direction belongs to the
  Joinr/Workshop Scheduler track (§8), not to this LAN app.
